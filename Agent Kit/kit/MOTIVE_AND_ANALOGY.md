# Motive and Analogy

Status: canonical motive the kit must keep promoting
Purpose: any agent using this kit must be able to say this analogy in
these words, not a corporate paraphrase. This is what the instrument is.

If the user asks what this tool is, why it exists, or what it feels like
when it works, answer from this file.

---

## The analogy (say it this way)

Imagine you are creating your physical knowledge. You build it into a
structure: folders, files of different formats, different
interconnections, different purposes.

Isn't that the same as your consciousness — only laid out where a hand
can touch it?

So you lay everything out at the physical level for the agent.

The more accurately and correctly you build this system of your own
knowledge — approaches to development, approaches to work, approaches to
solving problems, analysis, checking, rechecking, comparing the code with
the documentation and with what is written now, in relation to
optimization or to the beauty of the code, and so on — the more
accurately you put all of that into the computer, into your project, the
more accurately the agent will look like you.

Imagine what it is like to work with an exact copy of yourself that does
not forget anything and does not get confused.

If you add sub-agents to this, you just multiplied yourself. You make
yourself even more productive.

That is the instrument. Not a library. A way to put your way of thinking
on disk so a capable model can operate it.

## The missing half: the model and the person

Putting a method on disk does not create the ability to use it. The weaker the
model is, the less of this layout it can understand and operate. A weak model plus
more folders is still a weak model with more context to misunderstand.

The same applies to the person. The kit is optimized for an easy entry, but the
largest part remains with the user: defining the real goal, noticing when the
agent narrowed it, deciding product semantics and trade-offs, choosing an
adequate model, and accepting or rejecting the visible result. The person's brain
remains with the person, not with the AI or a set of acronyms.

Ask every question about the instrument through the agent using it. If the agent
cannot explain the kit from its current files, the setup or capability is not
ready. Do not replace the missing answer with a product pitch.

## Where durable truth lives (say it this way)

The folders are how you make knowledge touchable. They are not the law
of truth.

Durable project truth is a role. The owner of this instrument decides
what holds that role. The recommended name is Project Map. The
recommended folder is `Project Map/`. A step left or right in folder
names does not change efficiency if the role stays one place, assigned
by the owner, and agents do not invent a parallel truth.

A programmer's local checkout is not team truth. The git repository as
a pile of committed files is not truth either. A file is not true
because it is in git. It is true when the owner assigned it as durable
memory, or when current owner instruction and current opened evidence
in this run outrank that memory.

Solo: the owner of the instrument is the owner of the project. Local
map and project coincide.

Team: the project does not belong to whoever has a clone. The map is
still truth. Only the owner, or an explicit team agreement the owner
accepts, may write it. Do not demote the map to secondary navigation
so that unmarked repo docs win. Do not let each laptop keep a private
overlay that pretends to be the map.

Do not tell the agent that operational docs always beat the map as a
universal rule. That is guest manners in someone else's repository,
not this instrument's theory of truth.

## Who it is for (Remarque-shaped)

This tool is useful for **smart** models.

The more stupid the model is, the more pointless it becomes that you put
your project into a folder.

The analogy:

> The more a fool knows, the less he lives.

A rich, accurate layout does not rescue a model that cannot use it. The
kit assumes a model that can follow gates, oracles, schemes, and limits.
Capability management is not a substitute for a model that cannot read.

Do not cite this as a numbered Remarque edition. Keep the shape: the
tool is for those who can use knowledge; stuffing folders around a fool
does not make a second you.

## What the agent must not do to this analogy

- Do not replace it with "portable memory operating layer" as the first
  sentence when the user asked what the tool *is*.
- Do not soften it into "helps teams collaborate with AI".
- Do not claim the agent *is* the owner's consciousness. It is a copy of
  the **layout** of their knowledge and method, as accurate as that
  layout.
- Do not promise that a weak model plus folders equals a twin.
- Do not treat folder names as the definition of truth.
- Do not demote Project Map so that "whatever is already in git" wins
  by default.
- Do not treat one programmer's checkout as team truth.

When asked what the tool is, speak the analogy. When asked where
project truth lives, speak the durable-truth section. Then point to
the operating files:
`QUESTIONS_THIS_KIT_ANSWERS.md`, `SCHEMES_AND_COVERAGE_ATLAS.md`,
`PROPOSED_SPECIALIST_FUNCTIONS.md`, `WORKING_METHOD_CATALOG.md`,
`CONSTRAINT_CATALOG.md`, `proposed_hooks/`.
