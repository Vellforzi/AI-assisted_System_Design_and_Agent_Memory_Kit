# Human / Model Capability Contract

Status: canonical onboarding and routing boundary.
Purpose: make explicit what Agent Memory Kit amplifies, what it cannot manufacture,
and what remains the human owner's responsibility.

> [!IMPORTANT]
> **Agent Memory Kit is a multiplier, not a brain.** It can make a capable model
> and a capable owner substantially more effective. It cannot turn a model that
> cannot understand the task into a reliable executor, and it cannot replace the
> owner's judgment.

## 1. Ask the instrument through the agent

Questions about Agent Memory Kit should be asked through the agent that is using
it. A correctly installed agent must be able to answer, from current package
files:

- what the kit is and is not;
- where project truth lives;
- what the agent may do without another approval;
- which files, skills, gates and evals apply;
- what evidence proves completion;
- what remains the owner's responsibility;
- which capability or setup gap prevents the next step.

If the agent cannot answer those questions from the package, do not treat that as
a reason to invent an answer. Classify it as one of:

- the host did not load the kit;
- the required files are missing or stale;
- the selected model cannot use the available context reliably;
- the current execution surface lacks a required capability.

Repair or reroute the setup. Do not hide the failure behind generic wording.

## 2. The four-factor result boundary

Use this as a qualitative engineering model, not a numeric benchmark:

```text
result quality ~= model capability x constraint contour x current evidence x operator judgment
```

The factors multiply rather than replace one another:

- a capable model without grounding and gates can produce confident fiction;
- a detailed kit cannot manufacture reasoning that the model does not have;
- perfect files do not help when the host does not load or retrieve them;
- a strong model and strong kit can still implement the wrong product when the
  person gives an unclear outcome or accepts the result without judgment.

The weaker the model is, the less value it can extract from the kit. Below the
capability floor, adding more folders mostly adds context the model cannot use.

## 3. Model selection is result-first

Choose the model and execution surface for the required result, reasoning depth,
context and tool use. Apply this order:

1. Establish the minimum capability needed for the task.
2. Select a currently available model that meets that capability floor.
3. Select the surface with the required live tools.
4. Only then optimize price, latency and convenience.

Do not choose the cheapest model first and lower the quality standard to match it.
Do not use a premium model as ritual safety when a cheaper model has already
proved sufficient. Planning and execution may use different models.

Provider labels are volatile. A dated owner example from 2026-10-01 is: use
`Astra` for planning and `GPT-6 Sol` or `GPT-6.1 Sol` for execution when outcome
quality is the priority. Treat those names as an owner example, not a permanent
portable default; verify the current provider UI and capabilities before giving
current model advice.

Escalate or reroute when the current model repeatedly:

- loses the owner's qualifiers or causal chain;
- cannot reconcile contradictory evidence;
- invents project facts or product semantics;
- ignores the installed rules, gates or recovery fields;
- cannot preserve task state across the required context;
- produces plausible output without the required proof.

## 4. What remains with the person

The kit is optimized for a low-friction entry, not for removal of human
responsibility. The person's brain remains with the person, not with the AI or a
collection of acronyms.

The owner remains responsible for:

- the actual goal and why it matters;
- product semantics and material trade-offs;
- what must be preserved and what may change;
- selecting or approving the required capability level;
- maintaining or assigning durable project truth;
- granting side effects and credentials;
- judging owner-visible behavior;
- accepting, rejecting or redirecting the result.

The agent should reduce clerical load, preserve context, expose uncertainty,
execute authorized work and produce evidence. It must not pretend that those
functions transfer product ownership or judgment away from the person.

## 5. What the agent must say and do

When onboarding or advising the owner, the agent must make these boundaries hard
to miss:

- the kit improves a capable human-model system; it does not rescue an incapable
  model or an absent owner;
- questions about the kit are answered through the agent from the current kit;
- model choice is made for the required result before cost optimization;
- the owner still owns goals, semantics, trade-offs and acceptance;
- a capability gap is named and rerouted, not disguised as task completion.

Do not market the kit as autonomous intelligence, replacement judgment, or a
guarantee that any model will become reliable.

## 6. Adoption check

Before trusting an installation, ask the agent to explain:

1. what Agent Memory Kit is;
2. what it cannot do;
3. where current project truth comes from;
4. what model/surface it would choose for one real task and why;
5. what the owner must still decide and verify;
6. what would cause escalation to a stronger model or another surface.

An installation that cannot answer these from current files is not ready for
material work, regardless of how many folders, hooks or templates are present.
