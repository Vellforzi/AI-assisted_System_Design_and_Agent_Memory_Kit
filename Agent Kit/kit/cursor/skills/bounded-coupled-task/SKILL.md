# Bounded coupled task

Use for programming across files, languages, processes or components when
the owner-visible outcome is sufficiently defined. Multiple components alone
do not justify a full-product forensic investigation.

Apply $production-engineering-standard before engineering decisions and
through final review, including its required references. It owns dependency
contracts, independent test expectations, preserved invariants and verification
of the final deliverable. Before selecting, writing or interpreting checks,
read its applicable testing and verification guidance.
Resolve named skills through the active client's catalog; if a required skill
is unavailable, report that gap rather than claiming its workflow was applied.

## 1. Preserve authority and scope

Follow the current owner request and applicable project/task-class rules.
Preserve security, source identity, external-action and competing-writer
boundaries. Never bypass platform restrictions or safety controls.
Profiles, admission and receipts are evidence, not additional permission gates.

Add causally necessary local paths within the authorized outcome without
requesting duplicate approval. New product decisions or actions outside that
authority require an owner decision. Special restrictions on tests, fixtures,
harnesses, review, delegation and deployment override this workflow.

Commit/push, deployment, DB/Redis writes, credentials, Project Map updates
and other external actions require current authority; this skill grants none.

## 2. Execute coherent slices, finish the whole outcome

1. Identify the affected producer, transport/storage/state and consumer.
   Read the smallest complete dependency neighborhood and retain source
   references. Keep every acceptance criterion and preserved invariant.
2. When permitted and useful, reproduce the failure with a production-linked
   check before changing code.
3. Implement one coherent patch, preserving unrelated work. Repair actual
   failures without speculative cleanup.
4. Obtain the strongest safe authorized feedback for that component early.
   Check DB/cache/network/live side effects before execution: ordinary tests
   must not silently exercise production resources.
5. Review the diff and evidence proportionately. Establish checks or explicit
   gaps for both the requested result and affected existing behavior before
   combining further slices. The executor normally reviews its own work;
   independent review is optional when beneficial and permitted.
6. Continue through the complete authorized outcome. Internal slice sizes
   and planning counts are not acceptance caps or reasons to return early.

Use `SCOPE_EXPANSION_DECISION_REQUIRED` only for genuinely unapproved product
or action expansion, not ordinary causal discovery or a larger check set.

Source-only review is appropriate for read-only analysis, unavailable or
forbidden execution, and focused architecture/safety questions. Do not replace
an available authorized decisive check with repeated broad source review.

Do not weaken, delete or rewrite tests merely to make a patch pass.
For each new test, identify its criterion, independent oracle, distinct failure
mode and why existing coverage is insufficient.
If an existing test contradicts current owner-required behavior, report the
contradiction explicitly and change it only within that authorized semantic
delta.

## 3. Preserve and reuse evidence correctly

Retain source/artifact identity, actual commands/checks, results and coverage
gaps under the project's evidence policy. Keep complete relevant raw logs
when a runtime/forensic claim requires them; do not substitute summaries,
invent uncaptured evidence or collect unrelated journals. Exclude secrets.

Before reusing evidence, compare relevant file bytes, including dirty files,
and artifacts. A new causal gap invalidates only dependent results; do not
restart the whole inventory or unrelated checks without cause.

`inventory_generation`, elapsed-time targets and checkpoint/receipt counts
are diagnostics, not reasons to finish, create a new task ID, request approval
or escalate. `STOP_SOURCE_ONLY_LOOP` and `ORCHESTRATION_STALL` mean simplify,
obtain useful feedback and continue. Respect actual client limits and owner
deadlines; stop only for a genuine unresolved boundary.

## 4. Delegate only when useful and allowed

Follow the current delegation policy. Zero helpers is valid. Delegate only
a bounded subtask whose benefit exceeds transfer, waiting, checking and rework.
The parent owns connected reasoning, integration and final assessment.

Verify the actual suitable model/effort settings. Do not create mandatory
or recursive reviewer chains. Use one writer for overlapping files/shared
state; concurrent writes require authorized real isolation, not merely
different directory names.

Before assigning work to Cursor or interpreting its result, read
[Cursor worker protocol](references/cursor-workers.md).
Its scope, retry and result-admission rules are mandatory when applicable.

## 5. Continue safely and escalate for substantive reasons

Do not manually invoke summarize/compact. After interruption or compaction,
recover the owner goal, branch/HEAD, current source/write state, verification
and authority; reconcile partial effects before continuing.

Use `HANDOFF CHECKPOINT` only for unsafe unreconstructable effects or a real
execution blocker, not a context percentage or workflow counter.

Use $outcome-driven-task-closure for:
- an explicit owner request for full proof;
- repeated bounded repairs failing on the same causal surface;
- a safety-critical state invariant that cannot be localized;
- executable evidence exposing unresolved cross-system behavior;
- a regression recurring after local success;
- genuine forensic reconstruction.

Escalation adds no action authority. Report completed outcomes, material
changes/checks, significant worker contributions, exact blockers and remaining
evidence limits. Keep local checks, build, publication, deployment, runtime
and owner acceptance distinct. Bookkeeping is not delivery.
